## Typography Centralization Review

### Architecture (how it's wired)
- `content-typography.css` defines all type-role tokens at `:root` (not scoped to `.site-editorial`), and is imported by `SiteFonts.astro`.
- `SiteFonts.astro` is pulled in by both `Layout.astro` (every standard page) and `StandaloneMetadata.astro` (the hand-rolled standalone blog pages, e.g. `src/pages/blog/why-tech-hiring-really-takes-so-long.astro`). I confirmed both paths load it, so the tokens are actually available everywhere they're referenced — this is the one thing I was most worried about (a standalone page using `var(--type-section-size)` with the token undefined), and it checks out.
- `EditorialPage.astro`, `EditorialHeading.astro`, `Home.astro`, and the standalone blog page all consume the same `--type-hero-size` / `--type-section-size` / `--type-article-size` / `--type-subtitle-size` / `--type-card-size` variables, so the scale is genuinely shared rather than duplicated per component.

### Cascade robustness

**Real bug/risk found:** `src/layouts/Layout.astro` (lines ~228–288, inline critical CSS) and `src/components/candidates/CriticalStyles.astro` both contain hardcoded, `!important`-flagged hero-`h1` font sizes scoped to `.tribera-home .hero h1` / `.tribera-candidates .hero h1` (e.g. `clamp(36px, 4.6vw, 54px) !important`, `clamp(52px, 3.125vw, 60px) !important`). Neither `.tribera-home` nor `.tribera-candidates` wrapper classes exist anywhere in the current markup (`src/pages/index.astro` uses `V58Home` with no such class; `src/pages/candidates.astro` renders `Candidates.astro`, whose root is `.candidate-page` with a `.c-hero`, not `.hero`). This CSS is currently **dead** — it doesn't override anything today — but it's a latent trap: since it uses `!important`, if any future markup reintroduces a `.tribera-home`/`.tribera-candidates` + `.hero h1` combination (e.g. copy-pasted from an older branch), it will silently defeat `--type-hero-size` with a stale hardcoded value, and no test would catch it since these files aren't part of the reviewed set and the values look intentional (they're `!important`, not obviously vestigial). Worth deleting rather than leaving as a regression trap. This is outside the six files you named but directly threatens the robustness claim ("all active page hero ... size declarations were migrated") — it's technically true for *rendered* output today, but the assertion is fragile.

**Not a bug, verified fine:** `CustomStyles.astro` has a raw global `@media (max-width: 640px) { h1 { font-size: 1.75rem } h2 {...} h3 {...} }`. This looked concerning at first (untargeted element selectors could clash with token-driven headings), but specificity resolves it correctly — `.site-editorial :is(h1,.h1)` and `.v58-heading--h1` are both higher-specificity class-based selectors, so they win regardless of source order. No actual conflict today, but it's a second copy of "raw h1/h2/h3 mobile sizing" living outside the centralized system, which is confusing to read next to `content-typography.css` and could bite a future author who assumes global `h1`/`h2` rules are authoritative.

**Solid:** `content-typography.css`'s `:root` placement means no page can accidentally end up in a scope where the tokens are undefined; the `.site-editorial` and `.v58-heading` consumers only add family/weight/letter-spacing on top, they don't redefine the underlying size values, so there's a single source of truth for the numeric scale.

### Accessible hierarchy
- H1 → H2 → H3 sizes descend correctly (hero > section > card), and `EditorialHeading.astro`'s `h3` variant correctly maps to `--type-card-size`/`--type-card-leading`.
- `article.art h2` being deliberately smaller than the generic `.site-editorial h2` is implemented via a plain descendant override (`content-typography.css:204-207`) using the same token family (`--type-article-size`), so it stays in sync with the scale rather than drifting — good pattern for the "deliberately smaller" intent you described.
- `MarkdownLayout.astro`'s legal-document `h2` reuses `--type-document-size` with `--type-article-leading` (intentional per your note) and `h3` is a one-off `1.25rem` outside the token system — acceptable since legal-doc H3s are a minor, low-traffic secondary heading, but flagging it as an untokenized outlier for completeness.
- No accessibility regressions spotted in heading *order* (I didn't audit every page's heading sequence for skipped levels, since that's a content/authoring concern, not a typography-token concern).

### Test coverage (`tests/content-typography.test.mjs`)
Gaps, not correctness bugs:
1. **H3/card token is untested.** The script only inspects `h1,h2` (line 45); `--type-card-size` (used by `EditorialHeading--h3`) has zero automated coverage.
2. **Sub-360px override branch is untested.** `content-typography.css:18-23` shrinks `--type-hero-size`/`--type-section-size` at `max-width: 359px`, but the test's viewports are 390/768/1520 — that branch never executes under test.
3. **Subtitle selector list is a hardcoded allowlist** (line 66-69: `.v58-lead,.v58-thesis__body,...`). Any new subtitle-role class added later (e.g. a new page's `.foo__dek`) silently won't be checked unless someone remembers to add it here — not a bug now, but a maintenance trap given the "subtitle 18/16" role is meant to be universal.
4. The dead `.tribera-home`/`.tribera-candidates` CSS above wouldn't be caught by this test even if reactivated, since the test asserts computed size matches the token value on *whatever markup currently renders* — it can't detect "this selector exists but is currently unreachable and will misfire later."

### Verdict
The core token architecture is sound and genuinely centralized — one `:root` source of truth, consistently consumed across `EditorialPage`, `EditorialHeading`, `Home.astro`, and even the non-Astro-layout standalone blog pages (verified `SiteFonts` import there specifically because it looked like the highest-risk gap). The one actual finding worth acting on is the dead, `!important`-laden legacy hero CSS in `Layout.astro` and `CriticalStyles.astro` — it's inert today but is a regression time-bomb and should be deleted, not left as "just in case" code. Everything else (the `CustomStyles.astro` global h1/h2/h3 mobile rule, the untokenized legal `h3`, the test's allowlist/viewport gaps) is a cleanup/robustness preference rather than a live bug. I have not run the app or verified any of this in a browser — this is a static read of the code.
