# A2 delivery contract

New functions only; legacy handlers and shared guard behavior remain unchanged.

GET `contact-form-v9` / `sample-form-v9` returns a native form by default; `?format=json` returns `success`, `request_token`, `form_loaded_at` (string milliseconds), `expires_at`, `ready_at`, `min_submit_ms`, and validated `context`. JSON requests use `Accept: application/json`. Every response is no-store. Tokens have a fixed two-hour lifetime and must exactly match the server-issued timestamp. Wait until ready_at before submitting; never manufacture a timestamp. A token binds its form kind, not editable mode/context.

POST `contact-send-v9` / `sample-request-v9` accepts multipart, not JSON. All clients send the token, timestamp and empty `botcheck`; sample also sends empty `website`. Both honeypots reject400 explicitly. Contact requires side=hiring|looking, name,email; hiring also role,company with optional message; looking also one `cv`, optional note. Only active-side fields enter delivery. Extra recipient fields are ignored. Candidate uploads reuse existing10MiB multipart cap, PDF/DOC/DOCX signature validation and scanner; actual hosting body limits remain to be verified. Sample requires name,email,company and never subscribes the requester.

Context allowlists are exported as SECTORS/SERVICES from v9-a2-forms.mjs; intent only `sample-write-up`. Unknown POST context rejects. Native GET discards unknown context. It derives bounded context from a same-origin Referer only if none of side/sector/service/intent was explicit in query; an explicit blank query clears context. It compares protocol and host, not merely suffix. Referer never determines authorization or recipient. Native chooser shows context controls, allowing manual recovery when a browser omits its Referer.

Environment requirements (all environments): FORM_REQUEST_TOKEN_SECRET at least32 characters; RESEND_API_KEY; RESEND_FROM; CONTACT_HIRING_TO; CONTACT_LOOKING_TO; SAMPLE_LEADS_TO (only the relevant contact/sample recipient set required). No mailbox defaults. Token secret and explicit configured recipients must be supplied before the handshake; absent configuration returns503. Existing origin/rate/scanner environment settings still apply. No new package or bespoke storage service is required.

## Delivery and retries

Resend is the concrete durable deduplication provider, not process memory. Official documentation checked2026-10-19: https://resend.com/changelog/idempotency-keys and https://resend.com/blog/engineering-idempotency-keys . `Idempotency-Key` persists24hours; identical requests replay, differing payloads return409 invalid_idempotent_request, concurrent requests409 concurrent_idempotent_requests. The signed2hour acceptance window is shorter than that retention. Contact uses one key per token. Sample always sends/replays its requester-email step first, then sends/replays the lead email using a distinct deterministic key. The requester email includes every lead field/context; CV contact includes attachment bytes and checksum. This stops edited retries before secondary side effects. Provider JSON must contain a nonempty email id before success. No automatic new token, automatic retry or live delivery was used in tests.

A network error may occur after acceptance. Freeze the original fields/token and retry the identical request. Partial sample failure can mean the sample arrived but the team lead email did not yet; repeating the same token resumes safely. A different token means a new request and can send again: clients must not silently mint one after an ambiguous error. Tokens expire after2hours; expired requests cannot be resent under that token. If delivery remains uncertain, contact the team rather than opening a new request automatically. Config or PDF changes during this window can cause fail-closed provider payload conflicts; keep these stable during retries.

JSON: success200 `{success:true,message}`. Errors `{success:false,message,code,retryable}`. `validation`400 means no provider attempt, editing permitted. `expired`400 and `conflict`409 are terminal. `delivery`503 or concurrent409 is retryable with unchanged data; `scan`503 and `rate_limit`429 have no delivery effect. `configuration`503 is not completion. Native success303 redirects to a receipt GET; refresh cannot repeat a POST. Native failures retain the same hidden token and escaped text values. File inputs cannot be restored by a server: users must reselect the same original CV. No sensitive values enter redirect URLs.

## Private asset boundary

The exact handoff two-page PDF is copied to netlify/functions/\_assets/sample-write-up.pdf, not public/src. The sample-request-v9 function includes it via its netlify.toml included_files entry. Runtime reads its base-directory-relative bundled path. See https://docs.netlify.com/build/configure-builds/file-based-configuration/ . A local Astro build is not evidence that Netlify function bundling/delivery works; inspect the actual function artifact and validate the hosted configuration before publication. Tests compare attachment bytes to the handoff and mock all provider calls. No hosted deliverability, scanner readiness, or mailbox ownership is claimed.
